# StarStats engineering notes

Hard-won invariants and conventions. Most entries exist because something
broke in production; the incident is named so the reasoning survives.
Local-first personal Star Citizen metrics — Rust API + Next.js web + Tauri tray.

## Tech Stack
- **Monorepo:** pnpm workspaces (apps/web, apps/tray-ui, packages/*) + Cargo workspace (crates/starstats-{core,server,client}).
- **API:** Rust + axum + sqlx (Postgres) + JWT auth (claimed handle via `preferred_username`, device_id optional).
- **Authz:** SpiceDB (Zanzibar/ReBAC). 503 from SpiceDB-dependent endpoints surfaces as `spicedb_unavailable` banner.
- **Web:** Next.js 15 App Router (server components, server actions, useFormStatus). Auth via `getSession()` returning `{token, claimedHandle}`.
- **Desktop:** Tauri 2 (React+TS frontend, Rust backend). Tray owns the RSI session cookie — held in the OS keychain.
- **Spec:** utoipa derives OpenAPI; regenerate TS client via `pnpm --filter api-client-ts run generate` (script spawns `starstats-server-openapi` bin).
- **Audit:** `audit_log` is hash-chained, append-only. Share actions: `share.created | revoked | viewed | reported | report_resolved | visibility_changed`.

## Architecture Invariants
- **Server holds ZERO RSI credentials.** Only the tray scrapes `https://robertsspaceindustries.com/account/pledges` using the user's RSI cookie. Any "Refresh" affordance for hangar-style data MUST point at the tray (`/devices`), not promise a server-side fetch. HangarCard documents this; do not break the pattern.
- **Migrations are additive only AND byte-immutable post-deploy.** `IF NOT EXISTS`, NULL defaults, no DROPs, no NOT NULL on populated columns without defaults. Backward-compat parsing in Rust uses `#[serde(default)]`. sqlx hash verification covers the entire file — don't even reformat comments on a shipped migration (PR #37 production crash-loop, 2026-05-18).
- **Audit emission is best-effort.** Every audit `.append()` call wraps in `if let Err(e) = ... { tracing::warn!(...) }` so an audit hiccup never poisons the response.
- **Multi-endpoint web dashboards use `Promise.allSettled`**, not `Promise.all`. A single endpoint hiccup must not wipe the whole render. Log each rejection individually with `call=<label> status=<code>` so the failing endpoint is named in server logs.
- **SpiceDB rejects wildcard subjects in `CheckPermission` and `LookupResources`** (`InvalidArgument: cannot perform check/lookup on wildcard subject`). For schemas with `relation foo: user:*` — only `public_view: user:*` today — read existence via `ReadRelationships` filtered on the relation + subject. Pattern: `SpicedbClient::has_public_view` (single-tuple probe, fully-consistent) and `SpicedbClient::list_public_profile_handles` (enumeration via streaming `resource.object_id`). Writes (`WriteRelationships`) accept wildcard subjects fine. Bit `/v1/me/visibility` + `/v1/discover/profiles` simultaneously; fixed in `v1.5.4`.

## Conventions
- **Closed-vocabulary enums** stored as TEXT at the DB layer (e.g. ShareReportStatus, ShareReportReason). `parse()` + `as_str()` round-trip; adding a variant doesn't need a migration.
- **Trait + Postgres impl + Memory impl** pattern for stores (see `share_metadata.rs`, `share_reports.rs`). Memory impl lives in `mod test_support` and feeds route-layer unit tests.
- **Handle validation** via `validate_handle()` in sharing_routes.rs — ASCII alphanumeric + `_-`, ≤ 64 chars. Reuse before any SpiceDB write or DB lookup that takes a handle.
- **Per-share scope** stored as JSONB (`share_metadata.scope`). NULL = legacy `full`. Filtering on `allow`/`deny` event types uses ANY/ALL array predicates.
- **Server-side handle truth.** Sensitive form fields (reporter_handle, recipient_handle for the auth'd user) come off the bearer token / `session.claimedHandle`, never from the client. The client can supply the OTHER party's handle.
- **Server-action success chips derive from the response, not intent.** For mutating server actions (`<form action={fooAction}>`), build the post-redirect `?status=...` from the API response payload (e.g. `response.public`), not from the user's submitted form value (`wantPublic`). A 200-OK no-op (silent backend regression, future read-only mode, etc.) otherwise produces a green success chip on a page that still shows the old state — gaslights the user. Pattern: `visibilityAction` in `apps/web/src/app/sharing/page.tsx`. Surfaced 2026-05-21 by the SpiceDB wildcard-subject bug.
- **h1 type plateau (audit v2 §03):** `main h1` baseline = 28px (globals.css). Top-level pages opt to 32px inline. Detail pages can opt to 24px inline. Don't override unless the depth tier calls for it. **Mobile (≤640px):** `h1:not(.hud-tile__title)` shrinks to 26px and `h2:not(.hud-tile__title)` to 22px (starstats-tokens.css). The `:not(.hud-tile__title)` scope is load-bearing (M-W7): every HUD instrument-strip title carries `.hud-tile__title`, and the old bare `h1/h2 !important` used to beat those deliberate inline 14-18px sizes and blow them up on phones. New HUD strip titles MUST keep the `hud-tile__title` class to stay excluded.
- **Event headlines route through `humanTitleForEntry`** (tray `format.ts`, mirrored web-side). Never surface raw snake_case `event_type` as a user-facing headline. Layered fallback: server-formatted `summary` → curated `EVENT_VERB_TABLE` → sentence-cased `event_type`. The raw discriminant stays addressable as a tone-tinted chip + `title` tooltip + filter UI.
- **In-Transit movement noise is hidden at render-layer** in BOTH apps: tray `apps/tray-ui/src/lib/inTransitFilter.ts` (`isInTransitNoise`, wired into StatusPane's `shownTimeline`) + web `lib/event-filter.ts`. Keep the two suppressed sets in sync. Events still persist in DB — filter is display-only. **Path moved 2026-07-10 (M-U1):** the old `apps/tray-ui/src/timeline/` module was entirely dead code (nothing imported it) so In-Transit suppression was NOT actually applied in the tray; `IN_TRANSIT_HIDDEN_TYPES` moved to the live `src/lib/inTransitFilter.ts` and the dead module was deleted. Deliberate carve-out: the tray's raw Logs search (LogsPane) is left UNfiltered — it has explicit type pills, so hiding rows from a searched log would be user-hostile. Suppression applies to the derived StatusPane timeline only.
- **Two-gate model for cross-device toggles** (cloud sync, future similar features): local per-surface intent (`Config.sync_with_cloud` on tray) AND server-side authority (`devices.sync_enabled`). Both must be true for the action to proceed. Either side can withdraw consent; neither can force the other. Mirrors SSH keys + authorized_keys.
- **`apps/web` has vitest** (added 2026-05-21, mirroring tray-ui setup). Not Playwright-only. Tests live next to source files (e.g. `apps/web/src/lib/api.test.ts`); the `'server-only'` import is stubbed at `apps/web/src/test-setup-stubs/server-only.ts`. CI runs `pnpm --filter web run test:run` in the web job.
- **Playwright fixture default rule.** Any new authenticated layout-level fetch (anything called from `apps/web/src/app/layout.tsx` or a widely-rendered server component) MUST get a default fixture entry in `scenarioFor()`'s `base` map at `apps/web/e2e/helpers/api-mock.ts`. Without it, every existing scenario fails with `599 no_mock_fixture` on layout render.
- **Tauri 2 emit pattern.** `use tauri::Emitter;` is required in scope for `.emit()` (Tauri 1's `emit_all` is gone). Background workers that need to push events to React (e.g. `crates/starstats-client/src/sync.rs::spawn_lane`) must receive `AppHandle` (cheaply cloneable) and pass it through `start → respawn → spawn_lane`. New call sites of `respawn` (in `commands.rs::save_config`, `set_sync_preset`, `pair_device`) must pass it.
- **Marketing page convention.** New top-level marketing routes (e.g. `/features`) mirror `/about`: numbered eyebrow + h2 + lede + 3-4-card PointGrid sections. See `apps/web/src/app/features/page.tsx` for the canonical pattern. Top-level marketing h1 uses `clamp(40px, 6vw, 64px)`; section h2 uses `clamp(28px, 4vw, 40px)`.
- **`.ss-app` grid placement.** The signed-in shell is a 2-col CSS Grid (`220px rail | 1fr main`). Any direct child of `.ss-app` that should span the page (TopBar, footer, future full-width banners) MUST declare `grid-column: 1 / -1` — without it, auto-flow stuffs the element into the 220px rail column. TopBar does this in CSS (`.ss-topbar`); the signed-in footer does it inline in `layout.tsx`.
- **`.ss-topbar` flex child-order.** The topbar is a flex row where an element's on-screen position is the sum of every preceding sibling's width. Keep **variable-width** elements (the `RoutePlacard` route path, which changes per route) on the LEFT *before* the `flex:1` spacer so their width is absorbed there; keep **fixed readouts** (`LocationChip`, `AccountMenu`) *after* the spacer so they right-anchor and don't drift. Putting a variable-width sibling before a readout makes the readout slide sideways on every navigation — the "header stats move by page" bug fixed in v1.8.63 (`TopBar.tsx`: spacer moved between `RoutePlacard` and `LocationChip`). The chip therefore sits right, beside `@handle`, deliberately — don't move it back left without re-adding a spacer.
- **Signed-out marketing chrome lives in `layout.tsx`, NOT per-page.** `<MarketingNav>` (`apps/web/src/components/shell/MarketingNav.tsx`) is the canonical top chrome and is rendered globally from the signed-out branch of `app/layout.tsx` — the same way TopBar/LeftRail are for the signed-in branch. Marketing pages (`/`, `/features`, `/about`, `/lore`, `/privacy`, `/auth/*`) must NOT inline their own header. If you need page-active styling (e.g. highlighting Features on `/features`), do it via `usePathname()` inside MarketingNav. The signed-out footer follows the canonical **full-bleed-outer / max-width-inner** pattern: `.site-footer` (full-bleed, carries `border-top` that spans the viewport) wraps `.site-footer-inner` (capped at 1080px to match the marketing content column). Don't put `max-width` on the outer `<footer>` element — it produces a stripe-in-the-middle look on wide pages.
- **vitest config must mirror `tsconfig.json` `paths`.** `apps/web/vitest.config.ts` has both the `'server-only'` stub AND the `@/` → `./src` alias. Adding new tsconfig path aliases requires mirroring them in vitest.config.ts or every `@/foo` import in a test file 599s with "Failed to resolve import". Existing tests that imported via relative paths only worked by accident.
- **Tauri invoke arg names are byte-exact snake_case — but ONLY because every command declares `rename_all = "snake_case"`.** With the pinned toolchain (`tauri 2.11.3` / `tauri-macros 2.6.3`) a *bare* `#[tauri::command]` defaults its IPC keys to **camelCase** (`ArgumentCase::Camel`), and Tauri's key lookup is exact with no case fallback — a missing key for an `Option<T>` param silently deserializes to `None`, dropping the caller's intent without an error. So EVERY command in `crates/starstats-client/src/commands.rs` carries `#[tauri::command(rename_all = "snake_case")]`; TS invoke wrappers then send keys named exactly as the Rust fn params (`window_secs`, not `windowSecs`). Do NOT rely on any automatic camelCase↔snake_case mapping — it does not exist. Originally surfaced 2026-05-21 via `listTransactions(windowSecs)` (`v1.5.3` hotfix); the invariant was *inverted* by a later Tauri upgrade and corrected repo-wide on 2026-07-09 (C1) by adding `rename_all` to all 43 commands + normalizing the wrappers. Guard: `apps/tray-ui/src/ipc-arg-guard.test.ts` fails CI if any command drops the attribute or any wrapper sends a non-snake key. When adding a new command, include `rename_all = "snake_case"` and mirror the param names in the TS wrapper.
- **Fixed-position elements in tray panes MUST portal to `document.body`.** App.tsx wraps every pane in `<div className="ss-screen-enter">`, which has a CSS animation that applies a `transform`. Per CSS spec, any non-`none` `transform` creates a containing block for `position: fixed` descendants — so a fixed scrim/drawer/modal pins to that wrapper, not the viewport, and slides out of view when the inner content scrolls. Use `ReactDOM.createPortal(jsx, document.body)` to escape. Surfaced in LogsPane drawer fix (v1.5.2); the same trap applies to the sibling Status / Settings / Submissions panes.
- **The same portal rule applies to any popover inside a WEB widget tile** — for the mirror-image reason (clipping, not transforms). `.hud-tile` is `overflow:hidden` and `.hud-tile__body` is `overflow-y:auto`, so an `position:absolute` popover is clipped by BOTH plus `.ss-main`. `<InfoTip>` opened correctly for months and was invisible in every tile (v1.8.171 fix: measured popover at y=[177,290] against its own tile at [266,344] — it drew entirely above the tile). **Do NOT "fix" this by opening the containers**: `.hud-tile__body`'s `overflow-y:auto` is a deliberate safety net, and hud.css records that clipping silently swallowed travel's routes+map in v1.8.107. Portal to `document.body` + `position:fixed` from the anchor's rect, re-place on scroll/resize, and give the outside-click handler a SECOND containment check (a portaled popover is no longer inside the button's subtree).
- **CSS cannot override an inline style without `!important`.** Several components set `display`/`padding`/`gap` inline (`MarketingNav`'s link row, widget tiles). A stylesheet rule targeting them silently loses no matter how specific the selector. Two live bugs from this: the nav drawer's `display:none` never collapsed anything, and a narrow-desktop nav compression rule did nothing. If a rule "isn't applying", check for an inline style before adding specificity.
- **Never open a CSS comment with the word `!important`.** cssnano preserves "important comments" (the `/*! … */` legal-notice convention) and trims leading whitespace before testing for the bang — so `/* !important because … */` is classified as a licence header and shipped verbatim. One such comment was the only survivor in a 60KB production stylesheet (552B). Reword to put the word mid-sentence; the fix is one sentence, not deleting the explanation.
- **Dynamic SQL predicates in rusqlite.** When the WHERE clause depends on optional inputs (search query, type filter, cursor): push static `&'static str` fragments to a `Vec<&str>` based on which Options are `Some`, accumulate values in a `Vec<rusqlite::types::Value>` in lockstep, bind via positional `?`. NEVER interpolate values into the SQL template (injection risk + breaks rusqlite's prepared-statement cache). Reference: `Storage::search_events_paged` + `count_matching_events` in `crates/starstats-client/src/storage.rs`.
- **Tray Logs view data path.** Search + filter + pagination are server-side via `api.searchEvents` (case-insensitive substring against `type` and parsed `payload` JSON; optional exact `type_filter`; `id < before_id` cursor). Page size 200; the 10s auto-refresh ticks storage stats only — search results don't refresh on tick (would jerk the list mid-browse). Mutations explicitly re-run `refreshSearch` after success. Type-pill counts are label-only (per-type aggregates across whole DB would require N round trips). Detail drawer is portaled per the rule above.
- **Next 15 fetch data cache has a hardcoded 2 MB per-entry limit.** Any `fetch(url, { next: { revalidate: N } })` whose response exceeds 2 MB triggers `Failed to set Next.js data cache for {url}, items over 2MB can not be cached ({N} bytes)` on every render. The request still succeeds; the cache write is dropped silently. As of 2026-05-31, `/v1/reference/item` (~3.4 MB) and `/v1/reference/vehicle` (~4 MB) both trip it. Escape hatch in `apps/web/src/lib/reference.ts`: `LARGE_CATEGORIES` set drives `kbCacheOpts(category)` to return `cache: 'no-store'` for known-large categories, keeping `revalidate: 3600` for small ones. Add to the set if a future category crosses 2 MB; the symptom is the cache-warning log line. React's request-level fetch dedup still applies so same-URL fetches within one render share an upstream call regardless of cache mode.
- **Next.js fetch cache leaks across Playwright scenarios.** Both `fetch(url, { next: { revalidate: N } })` and `fetch(url, { cache: 'force-cache' })` opt INTO Next 15's URL-keyed data cache; the first response is reused across every subsequent test scenario that hits the same URL → mock fixtures don't swap and tests time out or pass with stale data. For fetches called from server components that multiple scenarios exercise (dashboard / journey / `/kb/*`), default to `cache: 'no-store'` to match the existing `apps/web/src/lib/api.ts` pattern, OR env-gate the cache directive (`STARSTATS_DISABLE_FETCH_CACHE`) so prod keeps the 1h cache and CI/test disables it. Reference: `apps/web/src/lib/reference.ts` (env-gated since v1.7.0). Surfaced 2026-05-22 on the KB-v1 listing fetchers — detail tests passed because each detail URL is slug-unique, but listing tests all hit `/v1/reference/{category}` and shared the first scenario's cache.
- **ReferenceCatalog is dual-keyed; iterate `list`, count via `counts`.** Since v1.8.0 hotfix, `getCategoryBundle()` keys each `ReferenceEntry` under BOTH `class_name.toLowerCase()` AND `display_name.toLowerCase()` (when distinct) — so `<EntityLink>` lookups resolve whether the caller hands in a raw identifier (`CRU_LEO`) or an already-friendly one (`New Babbage`). Consumers that iterate the catalog MUST use the canonical sources rather than `catalog.values()` / `catalog.size`: walk `CategoryBundle.list` (one entry per class_name) and read tile / facet counts from `loadAllReferenceBundles().counts.{cat}`. Walking `.values()` doubles every entry; reading `.size` doubles every count. Same dual-keying applies on the tray (`apps/tray-ui/src/lib/reference.ts`) — the tray's `findEntityInBundles` already uses the catalog directly, no change needed there.
- **`<EntityLink>` is the canonical wrapper for any web surface rendering an entity identifier.** Location, vehicle, weapon, item — wrap the rendered text in `<EntityLink category={cat} classKey={raw} catalog={catalogs.{cat}} label={existingFriendlyLabel} />`. The component handles every edge: no `classKey` → plain span; no catalog match → plain span; match without slug → display_name as plain span; match with slug → Link to `/kb/{category}/{slug}` + EntityHoverCard. Catalog prop is OPTIONAL — surfaces that don't have the fetch (tests, SSR paths) get plain-text fallback automatically. Established callers since v1.8.0: `event-summary-react`, `LocationPill`, `LocationHero`, `LocationChainStrip` / `ChainNode`, `LocationTimeline` / `TimelineRow` / `SystemChangeMarker`, `LocationChip` (topbar), `kb/[category]/page.tsx` card list. Tray equivalent: `<TrayEntityLink>` (`apps/tray-ui/src/components/kb/`) renders a button that calls `@tauri-apps/plugin-shell`'s `open()` on `${webOrigin}/kb/{category}/{slug}` — anchors can't navigate cross-origin under the WebView CSP. Pair it with `prettifySummaryReact` / `humanTitleForEntryReact` (`components/tray/format-react.tsx`) for ReactNode mirrors of the legacy string prettifier; string helpers retained for clipboard / share / OG-card paths. **Always pass the canonical display field as `classKey`, not a re-derived precedence.** When a component receives a `DistinctStop` (or any precomputed-display payload), use `stop.label` / `stop.sublabel` as the classKey — those are computed by `primaryLabel()` / `secondaryLabel()` and ARE the raw entity identifier of the chosen field. Re-deriving via `stop.city ?? stop.planet ?? stop.system` works for `label` (same precedence) but diverges for `sublabel` (case planet+system+no-city: sublabel = system, naive ?? chain = planet), so the catalog lookup hits a different entity than the displayed text. Symptom: link points to the wrong KB page or misses entirely when planet isn't catalogued but system is. Fixed 2026-05-22 in LocationChainStrip + LocationTimeline + LocationHero breadcrumb.
- **`<EntityLink>` on FREE-TEXT values MUST pass `label={value}`.** When `classKey` is a descriptive string rather than a clean identifier and the catalog has no match, EntityLink falls through to `toFriendlyName` (the class-id prettifier, `AEGS_Avenger_Stalker`→`Aegis Avenger Stalker`) which **rewrites the prose** — e.g. a contract attribute value `"a wreck site in the Glaciem Ring"` rendered mangled while clean values that happened to hit the catalog looked right (intermittent "sometimes maps" bug). Passing `label={value}` pins the displayed text to the verbatim value; EntityLink still adds a KB link on a genuine catalog match, but never rewrites. Applies anywhere free-text (attribute values, step locations, LLM-extracted descriptions) is wrapped. Fixed on the contract detail page in v1.8.57.
- **Next 15 dev server returns HTTP 200 for `notFound()` even when the not-found.tsx renders.** In production builds the status is correctly 404, but in `next dev` the body shows the not-found page while the headers stay 200. Playwright assertions targeting "this URL 404s" must check rendered content (`getByRole('heading', { name: 'Page not found' })`) rather than `resp.status()`. Production behaviour and user-visible UX are correct; only the e2e assertion shape needs to match dev-mode reality. Reference: `kb_detail_renders_not_found_page_when_endpoint_returns_404` in `apps/web/e2e/kb.spec.ts`.
- **Loadout is a SNAPSHOT, not a time series.** A `burst_summary` fires for ANY 3+ attachment run, so the LATEST loadout burst is often a partial re-equip. The `/me/loadout` page + widget pick the **fullest** burst (`pickFullestLoadoutBurst` in `lib/loadout.ts`, most items wins) and fetch `event_type=burst_summary` (denser than a 200-raw-event window); the widget is `rangeAware:false`. Non-gear is filtered by **port** (`isExcludedPort` — anatomy `*_ItemPort`/necksock + `radar`/mobiglas/`lens`), kept: `helmet_visor`, `eye_accessories`. Slot/group via `metadata.classification` (`FPS.Armor.*`→slot; `FPS.Weapon.*`/`WeaponAttachment.Magazine`/`Consumable.*`→groups). Item images same-origin only via `/kb/media/{cat}/{class}/{idx}` (never a raw `media.starcitizen.tools` URL); missing images degrade to name-only via the `<ItemImage>` client `onError`.
- **className'd components with no CSS pass every gate.** RTL `.toBeVisible()`/`getByRole` + e2e pass on unstyled-but-present elements — nothing asserts computed style. When adding new className-styled UI, GREP that the classes exist in a stylesheet (`apps/web/src/styles/hud.css` + `starstats-tokens.css`); a green suite does NOT prove it's styled. (Bit the paperdoll v1.8.49 — full-res unstyled images; fixed v1.8.50.)
- **e2e for an opt-in widget needs a profile-layout fixture.** Widgets `enabled:false` in `DEFAULT_LAYOUT` (loadout, hangar) won't render on `/me`; an e2e asserting them must override `GET /v1/users/me/profile-layout` → `{layout:[{id,enabled:true,size}]}` (mirror `profile-widgets.spec.ts`). The page route `/me/loadout` is NOT layout-gated.
- **Signed-in-page main landmark = `role="main"` on a DIV, NOT a `<main>` element.** globals.css ships a global `main { max-width:720px; margin:0 auto; padding:48px 24px }` legacy column for marketing/auth/legal/kb/contracts pages (the bare-`<main>` surfaces). Full-width signed-in dashboards therefore must NOT use the `<main>` element — it would clamp them into that 720px column. Put `role="main"` on the page's existing root `<div>` instead (same AT landmark, zero CSS collision). Exactly one main landmark per page: `app/admin/layout.tsx` provides `role="main"` for the whole admin surface, so admin pages must not add their own. Skip-to-content link lives once in `app/layout.tsx` (first in `<body>`, `.ss-skip-link`) and targets the `#main` wrapper on both shell branches. (M-W9.)
- **Destructive / mutating server-action buttons use `<ConfirmSubmitButton>`** (`components/forms/ConfirmSubmitButton.tsx`), not a raw `<button className="ss-btn ss-btn--danger">`. It composes `useFormStatus` (pending/disabled/aria-busy — kills double-submit) with an optional `confirm="…"` `window.confirm` gate, and passes `name`/`value` through for multi-submit forms (e.g. the admin share-report Dismiss/Revoke/Suspend row). NOTE: it (and any JSX-rendering component with a unit test) needs an explicit `import React` — the web vitest config uses the classic JSX runtime and 500s with "React is not defined" otherwise, even though the prod Next build (automatic runtime) doesn't. (M-W11.)
- **OpenAPI codegen drift gate:** in a multi-task change where >1 task touches a `#[utoipa::path]`, regen the TS client (`pnpm --filter api-client-ts run generate`) after the LAST one — a media/bytes endpoint still lands its PATH in the spec and trips the `OpenAPI codegen drift` CI job even though it returns no JSON.
- **"Animated background frozen on every page" = `prefers-reduced-motion`, not a bug.** `QuantumWarp` freezes by design under reduced-motion (12 frames then stop); a web deploy can't set the OS preference. Diagnose FIRST via console `matchMedia('(prefers-reduced-motion: reduce)').matches`; usual trigger is Windows **Battery Saver** forcing it. `toDataURL` reads the canvas buffer, so frozen-but-present ⇒ reduced-motion, gone ⇒ CSS/occlusion.
- **A widget that looks empty is a parser suspect, not proof of no activity.** `vehicle_stowed` fell from ~200/day to zero on 2026-07-14 when CIG renamed a `Game.log` shell tag, and stayed dark for three weeks while every test passed — the docking widget just looked like "you haven't docked". Diagnose in this order: (1) `/admin/parser-health` — the daily detector flags an event type whose share of all events collapses while the same users stay active; (2) the tray DB, `select type, count(*), max(timestamp) from events group by type order by max(timestamp)` — a type weeks behind the others is a dead classifier; (3) `unknown_lines.shell_tag` for a new tag first seen the week it died. Recover history via tray **Settings → Re-ingest rotated logs** (re-walks archives ignoring `tail_cursor`), THEN Re-parse. Re-parse alone is not a backfill: it promotes one stored sample per unknown *shape*, so thousands of missed lines recover as dozens. Prefer body-marker dispatch (`classify_body_prefix`) over shell-tag match arms for anything whose tag looks like an engine implementation detail.
- **Parser-health writes a heartbeat row every pass, including clean ones.** `parser_health_run` exists so "no findings" and "the detector is dead" are distinguishable; the admin page leads with last-run time for the same reason. The retention sweep's opposite choice (audit only when `deleted > 0`) is the bug being avoided — never infer health from the absence of records.
- **Build & Test cancel-chain on `main`.** GitHub Actions concurrency cancels in-flight runs when a newer push lands — so any active sequence of small commits to `main` (release-manifest auto-commits, docs catch-ups, fmt-fixes) means only the LATEST commit's run reaches its conclusion. Rust jobs are the long pole (3-4 min) and often get cut mid-run; release jobs are independent of `Build & Test` so binaries still ship while the gate is red. When chasing a gate-green, watch the run for the SHA you actually care about, not the run that happened to be in flight when you opened `gh run list`.

## Working agreements
- **Workspace clippy is `-D warnings`.** Every clippy warning is a CI failure. Workspace-level allows live in `Cargo.toml [workspace.lints.clippy]` with rationale; flip back to deny when a lint starts catching real smells.
- **`cargo fmt --check` is a CI gate.** Run `cargo fmt -p <crate>` after edits.
- **OpenAPI workflow:** edit handler + `#[utoipa::path]` + register in `openapi.rs` paths AND schemas; add `mod` stub to `bin/openapi.rs` for any NEW module; regenerate TS schema via `pnpm --filter api-client-ts run generate`.
- **New `Arc<dyn StoreTrait>` extensions:** mirror the `share_metadata_dyn` pattern in main.rs — Arc, dyn-cast, Extension layer added to the chain at the bottom of `app`.
- **Server bin names:** `starstats-server` (run) and `starstats-server-openapi` (spec gen). NOT `openapi` — that errors.
- **Branch model.** Two long-lived branches + two independent release tracks (split 2026-05-23):
  - `main` IS the live channel. Only ships-to-live code.
  - `next` is pre-release integration. Feature PRs target `next`.
  - **Two tracks, two tag schemas:**
    - **`tray`** (Tauri desktop client) — tags `tray-vX.Y.Z[-{alpha,beta,rc}.N]`. Version lives in `crates/starstats-client/Cargo.toml` (literal `version = "..."`, NOT `version.workspace = true`) + `crates/starstats-client/tauri.conf.json`. Manifest at `release-manifests/tray-{channel}.json`. Fires `release.yml`.
    - **`platform`** (server + web container images) — tags bare `vX.Y.Z[-{alpha,beta,rc}.N]`. Version lives in `[workspace.package].version` (drives `starstats-core` + `starstats-server` via `version.workspace = true`). Fires `release-images.yml`. No auto-update manifest (homelab pulls floating container tags via Komodo).
    - The `v*` glob excludes `tray-v*` naturally; tags never cross-fire.
  - **Per-track auto-alpha on push to `next`.** `promote.yml` runs `dorny/paths-filter@v3`; only the tracks whose files changed get tagged. Docs-only pushes tag neither. `starstats-core` changes trigger both (it's a shared dep).
  - **Invariant: `main` is a strict ancestor of `next`.** After every hotfix on `main`, run `node scripts/release-promote.mjs hotfix-finish` (track-agnostic) to merge `main` back into `next`.
  - **Tag-branch coupling enforced by `validate-tag` in BOTH `release.yml` and `release-images.yml`.** Pre-release tags must be on `next` but not on `main`. Live tags must be on `main`. Same rule, per track.
  - Promote via `node scripts/release-promote.mjs prerelease <tray|platform> <channel>` / `live <tray|platform>` / `hotfix-finish`. See `docs/RELEASING.md` quick-reference table.
  - **`release-images.yml` floating-tag routing.** `:latest` updates ONLY from a branch push to `main` (NOT from tag push). `:next` updates ONLY from a branch push to `next`. Tag pushes build `:<version>` + `:<sha>` only — they do NOT move floating tags. So "v1.8.6 tag exists on origin" doesn't imply the `:latest` container image has v1.8.6 content until the corresponding main-push CI completes successfully. If a deploy looks stale post-promote, check that the main-branch Release images run for the bump SHA succeeded — not just the tag-trigger run. **Skip rules are branch-aware (PR #111, 2026-05-27):** on `main`, only `release-manifests:` / `docs:` prefixes skip — bump commits proceed so live promotions correctly advance `:latest`. On `next`, the full skip list applies (auto-alpha bumps + manifest bots would otherwise waste runner time). Before PR #111, live promotes routinely left `:latest` stale because the head commit on main matched the bump pattern.
  - **`release.yml` GitHub Release flags: `prerelease` AND `make_latest` are independent.** Two pitfalls bit us 2026-05-27:
    1. The expression `contains(github.ref_name, '-')` was used to detect prereleases — correct under the pre-track-split scheme where bare semver had no hyphen, **broken** the moment tags gained the `tray-` prefix in 2026-05-23 (`tray-v1.8.8` now contains a hyphen unrelated to the channel). Use `contains(ref_name, '-alpha') || contains(ref_name, '-beta') || contains(ref_name, '-rc')` instead — robust against future tag-prefix renames.
    2. `gh release edit --prerelease=false` does NOT touch `make_latest`. After flipping a wrongly-flagged historical release, you must ALSO `gh release edit --latest` to grab the Latest badge. Future releases set `make_latest` explicitly at creation time so this isn't needed.
  - **`release-promote.mjs live` has a no-op guard.** When `next` and `main` are at the same SHA (e.g. after a hotfix back-merge or right after a live promote), the script refuses to bump: `[no-op] target SHA … is already on origin/main; nothing to promote (next has not advanced beyond main)`. Prevents empty pre-release tags. If you expected it to do work, push something to `next` first.
- **`RELEASE_PROMOTE_PAT` rotation requirements.** Workflow uses a PAT (not `GITHUB_TOKEN`) because tags pushed by `GITHUB_TOKEN` don't trigger downstream workflows (`release.yml` + `release-images.yml`). For rotation: **fine-grained PAT**, **Resource owner = `TheCodeSaiyan` (the org)**, scoped to the StarStats repo only, with `Contents: Read and write` + `Metadata: Read-only` (everything else unchecked — explicitly NOT `Workflows`). After a repo transfer between owners, the PAT MUST be re-issued under the new resource owner — a PAT scoped to your user can't push to an org-owned repo even if the URL slug is unchanged. Update via `gh secret set RELEASE_PROMOTE_PAT --repo TheCodeSaiyan/StarStats-Platform --body "<pat>"`. Verify with a `workflow_dispatch` dry-run + a real alpha promote (the no-op guard above will skip the push if next==main, so seed a divergence to truly exercise write).
- **Branch protection on `main` and `next`:** rebase, don't merge. (Currently convention-only; CI guards enforce ordering. Add server-side protection via the snippet in `docs/RELEASING.md` when convenient.) Release-manifest auto-commits show up between pushes — `git pull --rebase origin main` then push.

- **Commit type follows what the DIFF TOUCHES, not what the change is about.** `promote.yml`'s `decide` step skips auto-alpha on any commit whose first line starts with `docs:`/`docs(` (it exists so this document and memory edits don't spawn releases). A change to `apps/web/**` that is *documentation to the user* but *application code in the repo* must be `feat:`/`fix:` — committed as `docs:` it merges, runs `Detect tracks`, reports SUCCESS and ships nothing. Reserve `docs:` for `docs/`, this document and memory.
- **Verify a WEB deploy by the CSS content-hash, not `healthz`.** `api.starstats.app/healthz` reports the API container only; `starstats.app` is a SEPARATE container and has lagged it by 10.5 min (v1.8.171). The page HTML is served `no-cache`/`DYNAMIC` so it always comes from origin, and Next filenames are content-addressed — if fresh HTML still references the old `/_next/static/css/<hash>.css`, the web container has not rolled. That is not CDN staleness and re-fetching the asset won't help (assets sit behind a long CF cache and return `HIT` regardless).

## Do / Don't
- DO mirror existing store patterns (share_metadata → share_reports) when adding a new entity.
- DON'T trust a visibility or zero-overflow assertion to prove a layout bug is fixed. Both pass on broken code: a clipped popover is still `visibility:visible` (the ANCESTORS cut it), and an overflowing flex row `flex-wrap`s onto a second line instead of scrolling. Assert the property that actually differs — no clipping ancestor; hamburger and inline row never both showing; a header-height ceiling. Two live bugs (nav drawer, InfoTip) hid behind the obvious assertion.
- DO revert the fix and re-run when you write a test AFTER fixing something. A test authored against working code proves nothing until it has been seen to fail. This caught a real gap twice: the InfoTip "opens/closes" test passes either way, and a nav bound shaved to one platform's measurement failed CI by 7px.
- DO write 6-8 store tests against the Memory impl before wiring routes; route-layer tests come next using `tower::ServiceExt::oneshot`.
- DON'T fabricate server-side RSI fetch endpoints to satisfy a UX symmetry — reframe the affordance instead.
- DON'T amend a published commit; rebase + new commit only.
- DON'T `git push --force` to main.
- DON'T re-add ss-eyebrow as decoration. Two sanctioned uses only (L8 ruling, 2026-07-11): (1) a **section category label** above an h2 — one per section, never one per content card; (2) a **compact stat-tile label** — the small-caps caption above a single numeric readout in a stat tile (`PublicStatTile`, `HangarCard` stat rows). Both are terse labels for a value/section below them. NOT for prose eyebrows, per-card decoration, or repeating it under every tile in a grid of mixed content.
